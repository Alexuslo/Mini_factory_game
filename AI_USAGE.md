# AI_USAGE — Mini Factory (тестовое UnityDev, Dreams)

## 1. Использованные AI-инструменты

| Инструмент | Роль |
|---|---|
| **OpenCode** (терминальный AI coding agent) + модель **MiMo-V2.6-Flash-Free** | Основной инструмент. Агент работал **напрямую с кодовой базой** проекта (чтение, запись, запуск git, batchmode-прогоны Unity) — ровно то, что требует ТЗ п.8 |

## 2. Задачи, передававшиеся AI

- Разбор ТЗ и совместное проектирование архитектуры (обсуждение до строчки кода)
- Проектирование экономики кликера (формулы стоимости/дохода, балансировка)
- Полная реализация кода поэтапно: ядро (Core), игровая логика, сохранения, offline-прогресс, аналитика, UI-вьюхи, IAP-адаптер
- Генерация и поддержка unit-тестов (EditMode), прогон и диагностика падений
- Git-процесс: GitFlow-ветки, Conventional Commits, мержи `--no-ff`
- Диагностика багов по логам
- Сборка и диагностика Android-билда: разбор `logcat` при крашах, настройка Graphics API
- Базовое профилирование Android-билда (память/FPS через `dumpsys`, SurfaceFlinger)

## 3. Ключевые промпты (реальные, из диалога)

1. «перейди в D:\Home\Mini_factory_game изучи тз, переключись в план...» — старт: сначала разбор, потом код.
2. «по архитектуре сделать di на минималках, никаких сингл тонов. примерно - приложение владеет сервис локатором и раздаёт зависимости...» — фиксация composition root.
3. «необходимо разделение - MVC подойдет. Используй систему событий...» — выбор MVC + событийной реактивности.
4. «необходим data-driven подход, никакого хардкода, все настройки живут в конфиге...» — требование конфигурируемости без правки кода (п.3 ТЗ).

## 4. Реализовано с помощью AI

- Структура проекта и все asmdef (Core / App / Tests / Editor), включая правило `noEngineReferences` для ядра
- Весь gameplay-код: `FactoryModel`, `EconomyService`, `GameController`, `OfflineCalculator`, `GameLoop`
- Persistence: `PlayerProgress`/`JsonSaveService` (+ guard автосейва до инициализации)
- Аналитика: `AnalyticsService`, `ConsoleAnalyticsProvider`, набор событий
- Unity IAP 5.4.4: `IGamePurchaseService`, `UnityIapService`, продукты из конфига, все ветки ошибок
- Весь UI: вьюхи, префаб карточки, `SceneBuilder` (в т.ч. ScrollRect-список, UI-секция конфига)
- Титульный экран (логическая часть: `StartReport`, `HasSave`, `RestartProgress`)
- A/B-эксперимент (`ExperimentSelector`, `ExperimentConfigSource`) и debug-панель
- 39 EditMode-тестов (экономика, offline, сейв, контроллер, A/B, аналитика, туториал, UI-конфиг), включая тесты IAP через фейковый сервис

## 6. Изменённые и отклонённые предложения AI

| Предложение AI | Решение кандидата |
|---|---|
| Zenject / DI-фреймворк | **Отклонено.** Вместо этого composition root + конструкторы — меньше кода, проще тесты, соответствует масштабу |
| Менеджеры-синглтоны  | **Отклонено**  все зависимости через композитор |
| TextMeshPro для UI | **Изменено** на встроенный `UnityEngine.UI.Text`: TMP требует Essential Resources, мешает batchmode-сборкам |
| IAP 5.6.0 (последняя) | **Изменено** на 5.4.4 — 5.6.0 не резолвится для редактора 6000.3.22f1 |
| Сложная A/B-миграция сохранений при разном количестве машин | **Упрощено**: переключатель деструктивный + предупреждение в debug-панели; полная миграция — только вместе с фичей A/B |
| Коммитить `Assets/MiniFactory/Editor/` | **Изменено** — скрипт локальный, в `.gitignore`, чтобы ревьюер видел только релевантный код |

## 7. Некоторые ошибки и спорные решения AI, обнаруженные при разработке

1. **Коллизии неймспейсов с Unity API**: `App.Time` vs `UnityEngine.Time` → переименовано в `App.Timing`; `IPurchaseService` vs `UnityEngine.Purchasing.IPurchaseService` → переименовано в `IGamePurchaseService`. Правило проекта: переименовывать, не квалифицировать.
2. **Корневая причина «пустого экрана»**: `EditorSceneManager.NewScene` инвалидирует ссылки на ассеты, взятые до него — `configAsset` и `cardPrefab` записывались в сцену как `{fileID: 0}`. Найдено по логам; фикс — перечитывать ссылки через `AssetDatabase.LoadAssetAtPath` после NewScene.
3. **Гонка сейва при A/B-переключении**: AI написал переключатель варианта в debug-панели, который писал вариант напрямую в файл, в то время как `GameController` держал свой вариант в памяти и при следующем автосейве затирал запись старым значением. Поймано только ручной проверкой; фикс — синхронизация варианта через `SetExperimentVariant` в контроллере.
4. **Краш билда на эмуляторе**: `SIGSEGV` в потоке `UnityGfxDeviceW` при старте (лог `logcat`). Причина несовместимость Vulkan с BlueStacks; фикс — явный OpenGLES3 в Graphics API на Android. `dumpsys gfxinfo` при этом оказался бесполезен для Unity (рендер мимо HWUI) — FPS считался через `dumpsys SurfaceFlinger --latency`.
5. **Ошибки вёрстки**: все настроено вручную, создан реалтайм конфигуратор.
6. Мелкие ошибки компиляции, пойманные на прогонах: забытый `using`, `:` вместо `=` в initializer, неверное ожидание в тесте (cost 115 vs 100), устаревшие имена API Unity.
7. Предупреждения CS0618 (obsolete API Unity IAP v5) — оставлены осознанно: FakeStore работает, миграция API не даёт ценности для тестового.

## 8. Инцидент и восстановление (как пример работы с AI-инструментами)

Во время разработки основная сессия OpenCode в GUI-приложении оборывалась во время пиковой нагрузки (streaming 502), упал терминал. Контекст (~280 сообщений, 2 авто-саммари компакций) был **восстановлен из локального SQLite-хранилища opencode** (`~/.local/share/opencode/opencode.db`, таблицы `session_message`) и перенесён в план работы (`ПЛАН.md`). Продолжение разработки велось новой сессией в терминале с подхваченным контекстом.

## 9. Принцип работы (для ревьюера)

AI использовался как **агент, пишущий код по согласованным решениям**: каждая архитектурная развилка обсуждалась и утверждалась человеком до реализации; человек тестировал результат в редакторе и возвращал баги, с инструкцией исправления. Ограничение «≤5 часов фактической работы» соблюдалось по фактическому времени активной разработки.
